## 1. The spend cap cannot fire. Rule 7 is unenforced on this installation. — HIGH

```sql
SELECT ROUND(SUM(cost_usd),2) FROM model_call WHERE started_at >= '2026-08-01';
-- 376.96
```
against `monthly_spend_cap_cents = 5000` ($50.00).

**This is not a bill.** `MODEL_BACKEND=claude_cli` reports what each call *would* have cost
on the API; the subscription is what is actually paid. `sync.py:185`:

```python
return not self.imputed and self.total_cents >= self.cap_cents
```

`imputed` is true for `claude_cli`, so `reached` is **always False** — by design, from the
2026-08-03 fix that stopped the cap freezing extraction over money nobody was billed. The
consequence is that CLAUDE.md rule 7 ("spend cap is enforced in code") describes nothing
that is currently running: there is no ceiling of any kind.

**The trap on the other side.** The instant the backend changes to a billed one, the cap
reads the same $376.96 of *historic imputed* spend as this month's total, trips on the
first call, and the pipeline degrades to triage-only permanently. Switching backends is
therefore a two-line change: the backend, and the recorded history the cap sums.

## 2. The failure signal is saturated — sync has exited non-zero every run since 02:13Z — HIGH

```sql
SELECT id, started_at FROM run WHERE errors_json LIKE '%immutable%' ORDER BY id LIMIT 1;
-- 490 | 2026-08-21T02:13:22+00:00
```

Every run since emits the same five errors and exits 1:

```
content changed for an immutable source_item: canvas:ics:assignment:7833000
… 7833001, 7833003, 7833004, 7833134
```

These are the five CIS 236 assignments whose due dates moved upstream. `source_item` is
immutable (migration 0002), so `upsert_source_item` records the conflict and skips — and
because the feed will disagree with the stored item *forever*, the conflict re-fires every
30 minutes, permanently.

Rule 5 says a failing source exits non-zero so a scheduled run reports failure. That
signal now reads "failed" continuously, which means **a real failure is no longer
distinguishable from this one**. `launchctl list` shows `com.backglass.sync` last exit 1.

Two things worth being precise about:

- **This is not fixed by goal 4 increment B.** B moves the *commitment's* due date. The
  conflict fires in `upsert_source_item` at ingest, before commitments are touched, and
  will keep firing after B lands.
- **It grows.** Every future upstream date change adds another permanent error for the
  rest of the semester.

The fix shape is a once-per-`(external_id, new content_hash)` identity for the conflict
report, so a known disagreement is stated once and not re-announced 48 times a day.

## 3. Source health is last-run, not a rate — a source failing 90% of runs reads green — HIGH

`backglass doctor` reports all nine credentials healthy. Over the same period:

```sql
SELECT substr(started_at,1,10) d, COUNT(*) runs,
       SUM(errors_json LIKE '%reminders:%')   reminders,
       SUM(errors_json LIKE '%apple-notes:%') notes,
       SUM(errors_json LIKE '%apple-contacts:%') contacts
FROM run WHERE started_at >= '2026-08-18' GROUP BY 1;
```

| day | runs | reminders | notes | contacts |
|---|---|---|---|---|
| 08-19 | 13 | 5 | 0 | 0 |
| 08-20 | 31 | **28** | 3 | 3 |
| 08-21 | 31 | 4 | 7 | 0 |

`reminders` failed 28 of 31 runs on 08-20 and `credential.status` still says `ok`, because
`mark_ok` runs on any successful fetch and the *most recent* one happened to succeed. The
2026-08-21 lesson already says a degradation is only as good as somebody reading it; this
is the same failure one layer up — the reading surface itself averages to green.

The rate data already exists in `run.errors_json`. Doctor should report a trailing-window
failure rate per source, not the last verdict.

Underneath it is the known osascript timeout family (the 120s subprocess limit against
scripts measured at 80s–2:02 on an *idle* machine). `apple-notes` has collected nothing
since 2026-07-31.

## 4. 170 of 368 open commitments are below the confidence threshold and invisible to the planner — MEDIUM

```sql
SELECT COUNT(*) FROM commitment WHERE status='open' AND confidence < 0.7;  -- 170
SELECT COUNT(*) FROM commitment WHERE status='open';                       -- 368
```

`planner.candidates` filters `c.confidence >= settings.confidence_threshold`, so 46% of the
open ledger can never be scheduled. Rule 2 is working as designed — low-confidence
extractions belong in a review queue, not the brief — but the queue is not being drained,
and a review queue nobody empties is indistinguishable from a leak. 63 rows are also
overdue.

## 6. The 30-minute loop is really "30 minutes while the Mac is awake" — MEDIUM

`StartInterval 1800`, so 48 runs a day nominal. Actual: 31 on 08-20, 31 on 08-21. Gaps
over three hours in the window:

```sql
SELECT a.started_at, (julianday(b.started_at)-julianday(a.started_at))*24 hours
FROM run a JOIN run b ON b.id = a.id+1
WHERE a.started_at >= '2026-08-14' AND (julianday(b.started_at)-julianday(a.started_at))*24 > 3;
```

Six overnight gaps of 11–12 hours, and one **33-hour outage** from 2026-08-18T07:21 to
2026-08-19T16:42. `StartInterval` does not fire while the machine sleeps and launchd
coalesces the missed firings into one. The self-healing work (`schedule.ensure_loaded`)
covers a job that is *unloaded*; it does not cover a job that is loaded and asleep.

Not necessarily a defect — but "the sync runs every 30 minutes" is not true, and anything
reasoning about freshness should read the last run rather than assume the cadence.

## 7. Minor

- **`model_call` misses CLI-initiated passes.** The `Metered` calls list is never persisted
  outside `sync`, so `backglass relevance` / `recheck` runs under-count. A cap audit reads
  low by however much was done from the terminal. (Known, noted in `tasks/todo.md` §10.)
- ~~**One date-pinned test**, "fails only on 2026-08-20, self-heals tomorrow".~~
  **Corrected, and it was a real bug in `notify.py`, not in the test.** It did not
  self-heal — it failed every day from 2026-08-20 onward. `_notify` wrote
  `notification.created_at` from the wall clock while taking `local_date` from the
  caller's injected `now`, so a row's own two timestamps came from two different clocks.
  `_stale_questions` then compares a question's `asked_at` against that column, under a
  docstring that claims "both timestamps come from now_iso(), so the comparison is one
  clock against itself" — which was exactly what it was not doing. Production was
  unaffected (there the two clocks agree), but the re-banner rule could not be tested
  honestly, and the suite carried a permanently red test. Fixed: `created_at` now derives
  from `now`. Suite is 2334 green with nothing deselected.
- **Lint debt**, all pre-existing: `duplicates.py` B023 (loop variable not bound in a
  closure — a real bug shape, worth a look), `state.py` F402 shadowing, several E501.
- **Today's $25.76 is explained and benign.** 146 extract calls in the 01:00Z hour against
  153 `canvas:ics` items ingested the same hour, all kept — a one-time backfill of the full
  Canvas feed, extracted once each. Calls in the following hours: 2, then 2. Not a loop.

## Suggested order

1. Conflict identity (#2) — restores the failure signal, which everything else is read
   through.
2. Doctor failure rates (#3) — the reading surface has to be trustworthy before the
   osascript timeouts underneath it can be judged.
3. Spend-cap decision (#1) — required *before* any backend change, not after.
4. Review-queue drain (#4), brief delivery (#5).

## Addendum — found while switching the model backend to OpenRouter (same day)

The owner's ruling: run the pipeline on OpenRouter's free tier. Four things surfaced that
belong in this audit because they were latent before the switch, not caused by it.

### A. `MODEL_BASE_URL` was answering two different questions — HIGH

One setting supplied both the chat endpoint and the `/v1/embeddings` endpoint
(`search.py:143`). Pointing chat at OpenRouter would therefore have sent embedding calls
there too, where `nomic-embed-text` does not exist: every index run dead on a 404, and any
vector that *did* return belonging to a different model's space than the 1,248 already
stored — which the `embedding` identity forbids and which returns plausible nonsense
rather than an error.

Split into `EMBEDDING_BASE_URL`, falling through to the chat URL when unset so every
existing config keeps its meaning. Caught by reading `Settings` back after writing `.env`,
not by a test — the symptom was `base_url` resolving to Ollama when it should have been
OpenRouter, because a later duplicate line silently won.

### B. The client discarded the one thing that made a failure diagnosable — MEDIUM

`DeepInfraBackend` raised `ModelError("deepinfra returned HTTP 400")` and dropped the
response body. The actual message was `'models' array must have 3 items or fewer` — a
one-line fix behind an unreadable error, on a path where *every* call fails identically.
The body is now read into the error, truncated.

### C. OpenRouter caps routed models at three — MEDIUM

Discovered by the above. `MAX_ROUTED_MODELS = 3` is now enforced in code rather than
trusted to whoever edits `MODEL_FALLBACKS`, because the failure mode is total.

### D. Free-model availability flaps within the minute — context for #1

Measured across all 16 free tool-capable models: five answered `429 … temporarily
rate-limited upstream` inside the same minute six others served, including the model
chosen on paper an hour earlier. Three more returned a *valid* tool call containing zero
commitments for a message holding two — a silent miss, which is worse than an error
because nothing surfaces it. One rejected the extraction schema outright (422).

This is why `MODEL_FALLBACKS` exists and why `scripts/openrouter_shootout.py` is kept: the
question "which free model can run this pipeline" has to be re-measured, not remembered.

### Follow-ups this created

- **`MONTHLY_SPEND_CAP_CENTS=45000` expires on 2026-09-01.** It is raised only to clear
  August's $419.33 of imputed claude_cli spend, which the cap would otherwise read as a
  bill. Put it back to `5000` when the month rolls; $450 guards nothing.
- **The real fix for #1 is a per-run `imputed` flag** so the cap sums billed spend only,
  and imputed history stops being able to stop a billed backend. Deliberately not done
  here: inferring the flag for existing rows would be wrong for any installation that has
  actually been billed, and this repo ships publicly.

  Anthropic-only. No batch job is currently scheduled, so nothing is broken today.
