# Three fixes, 2026-08-23

Owner: *"the app doesnt schedule every day still says there are 173 items that dont work"*

Both complaints were already diagnosed in this repo and neither had been fixed. What
follows is the code half; the timezone half is a reboot and no code can do it.

## 0. Not a code fix: the reboot

Every `StartCalendarInterval` job fires ~11h30 late — plan 05:45→17:15, brief 06:00→17:30,
backup 02:00→13:30. Uniform offset across every job is the stale timezone in
`com.apple.UserEventAgent-Aqua` (`tasks/lessons.md` 2026-08-17,
`tasks/product-gaps-2026-08-20.md` §1). SIP refuses to restart that agent and `launchctl`
reload inherits the stale zone. **Only a reboot clears it.**

What has been carrying the day meanwhile is the 30-minute sync timer, through
`catchup.run` — today's plan (day_plan 73) was written at 08:45, not 05:45.

## 1. An empty proposal must not supersede a working plan — `plan/planner.py`

The 05:45 job deliberately omits `--if-missing` so the overnight-batch plan can replace a
thinner pre-dawn one. Firing at 17:15 inverts that: the clock clamp finds no hours left,
proposes capacity 0 / planned 0, and supersedes the good plan.

Measured: day_plan 71 (13:23, capacity 181, planned 225) superseded by 72 (17:15, capacity
0, planned 0, overflow 188). Same on 2026-08-21 — rows 67, 68, 69 all capacity 0.

- [ ] `persist` refuses to supersede a live plan that scheduled work with a proposal that
      schedules none. Returns the standing plan's id. `force=True` for the owner's own
      `/schedule/{date}/replan` click, which must always win.

## 2. Canvas due dates move and the commitment never follows — `coursework.py`, `ledger.py`

`canvas_ics` puts the due date in `body_text` *and* `occurred_at`, both hashed. When Canvas
moves a date the re-read is a `content_hash` conflict on an immutable row: recorded,
skipped, **propagates nothing** — and re-announced on every sync since 2026-08-21, which is
why the job has exited non-zero every 30 minutes.

| `7833000` CIS236 1-1-1 | 2026-08-25 | id 356 — 2026-08-23 |

Migration 0031 already gave the mutable half a home and `coursework.upsert` already writes
the new date and notes the move. Nothing carried it to the obligation the planner reads.
Migration 0032's own note names this as the next wiring pass.

- [ ] `SourceItem.mutable_upstream` — a differing hash on such an item is news, not a fault.
      `canvas_ics` sets it; the ledger routes it to `source_item_revisions`.
